# YouTube Multi-View SaaS

Paste one YouTube link (or raw video ID) and render it up to 100 times on a single
muted page with selectable layouts, per-player repeat counts, batch transport
controls and lazy loading.

Built with **Next.js 14 (App Router)**, **TypeScript**, **Tailwind CSS** and
**react-hot-toast**. No database or API keys required — sessions live in memory
and preferences in `localStorage`.

## Getting started

```bash
pnpm install
pnpm run dev     # http://localhost:3002
```

Other scripts:

```bash
pnpm run typecheck  # tsc --noEmit

```

## How it works

1. Paste `https://www.youtube.com/watch?v=…`, `https://youtu.be/…`, a
   `shorts`/`embed` link, or a bare 11-character ID. The field validates locally
   for instant feedback, then confirms through `/api/validate-url`, which also
   resolves the video title from YouTube's public oEmbed endpoint.
2. Pick how many players you want (**Number of Embeds**: 20 / 30 / 50 / 100),
   choose an **Autoplay Repeat Time** (how many times each player plays the video
   before pausing itself), toggle autoplay, then choose a layout.
3. Press **Start Multi-View**. Embeds are generated by
   `/api/generate-embeds` (with a local fallback if the API is unreachable).

Audio is **always muted**: `mute=1` is hard-coded in every generated embed URL,
independent of the autoplay setting.

## Layouts

| Mode | Columns |

## API

| Endpoint | Body | Response |
| --- | --- | --- |
| `POST /api/validate-url` | `{ url }` | `{ valid, videoId, title }` |
| `POST /api/generate-embeds` | `{ videoId, count, autoplay, layout, startSeconds? }` | `{ sessionId, embeds }` |
| `POST /api/save-session` | `{ sessionId, configuration }` | `{ saved, sessionId }` |

All three routes validate input, sanitize strings, whitelist the embed count and
layout, and apply a simple in-memory rate limit.

## Player controls

Embed URLs include `enablejsapi=1`, so **Play All / Pause All** and the per-player
play/pause buttons drive the YouTube players over `postMessage` without loading
the IFrame API script. Individual players are mounted lazily through
`IntersectionObserver` (the first rows render immediately; the rest mount as they
scroll in).

## Autoplay Repeat Time

`Number of Embeds` decides how many players are on the page; `Autoplay Repeat Time`
decides how many times **each** player plays the video. Options are **Once (1)**,
**3×**, **5×**, **10×** and **20×**.

`utils/playerController.ts` implements it over the same postMessage protocol the
official IFrame API uses internally — no API script is loaded:

```js
// parent → widget
{ event: 'listening' }
{ event: 'command', func: 'addEventListener', args: ['onStateChange'] }

// widget → parent
{ event: 'infoDelivery', info: { playerState: 0 /* ended */, currentTime: 12.3 } }
```

Every player is watched by a single window-level message listener (bindings are
keyed by `event.source`, so 100 players cost one listener). On `playerState === 0`
(ended) the player either seeks to 0 and plays again, or — once the repeat count is
reached — is paused and left stopped. Each tile shows a `↻ 2/3` badge while it
repeats.

## Notes and limits

- Sessions are stored in memory, so they reset when the server restarts. Swap
  `lib/sessionStore.ts` for MongoDB/Supabase to persist them.
- Browser autoplay policies often require a user gesture before multiple muted
  players start; the dashboard warns about this in the sidebar.
- Heavy counts (100 players) are intentionally unvirtualized — iframes must stay
  mounted to keep playing. Lazy mounting is the main mitigation.
- Repeat counts depend on the widget's `infoDelivery` state stream. If a browser
  blocks the postMessage handshake, players simply behave like normal one-shot
  embeds.
